# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm ci                         # install deps (Node.js 22+)
npm run dev -- --ip 127.0.0.1  # local dev server at http://127.0.0.1:8787 (reads/writes REAL WebDAV)
npm test                       # run all tests (node:test, no framework)
node --test test/webdav.test.mjs                        # run one test file
node --test --test-name-pattern '分页' test/webdav.test.mjs  # run one test by name
npx wrangler deploy --dry-run  # verify the Worker bundles without deploying
npm run deploy                 # wrangler deploy to Cloudflare
```

There is no linter or build step. Tests are plain `.mjs` files under `test/` using `node:test` + `node:assert/strict`, with `fetch` stubbed by passing a fake request function as `new WebDAVStorage(env, fakeFetch)`.

## Configuration

Local secrets live in `.dev.vars` (git-ignored; `cp .dev.vars.example .dev.vars` then `chmod 600`). Required vars: `WEBDAV_URL` (credential-free, query-free HTTPS root, e.g. `https://example.com/dav`), `WEBDAV_USERNAME`, `WEBDAV_PASSWORD`, `AUTH_TOKEN`. Optional non-secrets in `wrangler.toml` `[vars]` (overridable in `.dev.vars`): `TIMEZONE_OFFSET` (hours, default 8) and `MAX_UPLOAD_MB` (default 95) — the latter only drives the dashboard's pre-flight size check; the real ceiling is Cloudflare's per-plan request-body limit, enforced at the edge before the Worker runs, so raise it only when the account plan actually allows more. In production these are set individually via `npx wrangler secret put <NAME>`; `.dev.vars` is never deployed.

`AUTH_TOKEN` guards the app's upload/list/delete endpoints and is independent of the WebDAV password. If `AUTH_TOKEN` is unset, `AuthMiddleware` fails open (no auth) — always set it. **`POST /mcp` is the one exception: it fails closed with a 503 when `AUTH_TOKEN` is unset.** An unauthenticated MCP endpoint is not merely an open image host — it is a remotely driven, LLM-controlled server-side fetcher that will retrieve any URL an attacker names and persist the bytes at a public address, i.e. an open proxy plus an open write primitive, discoverable by anyone who tries `POST /mcp`. The global fail-open semantics are deliberately left alone (flipping them would silently break deployments running without a token); a repo-wide fail-closed migration should be its own announced change. `/oauth/*` and `/.well-known/oauth-*` fail closed the same way — without `AUTH_TOKEN` there is no signing key.

`AUTH_TOKEN` now carries a third job on top of being the bearer credential: it is the HMAC key every OAuth artefact is signed with, **and** the password typed into the consent page. Rotating it therefore revokes every issued `client_id`, authorization code, access token and refresh token in one move — which is the only revocation mechanism this stateless design has. Expect every OAuth client to need re-authorization after a rotation; `Bearer <AUTH_TOKEN>` clients just need the new value.

## Architecture

Single Cloudflare Worker. `src/index.js` is a hand-rolled router (path + method `if` chain) that builds `new ImageService(new WebDAVStorage(env), env)` per request and dispatches.

**Storage abstraction is the key design point.** `ImageService` is storage-agnostic and depends only on an R2-`Bucket`-shaped interface: `get(key)` → `{ body, httpEtag, writeHttpMetadata(headers) }` or `null`; `put(key, body, { httpMetadata })`; `delete(key)`; `list({ prefix, delimiter, limit, cursor, order })` → `{ objects, delimitedPrefixes, truncated, cursor }`. `order` (`'asc'` default / `'desc'`) is a WebDAV-branch extension: native R2 silently ignores it, so `main` / `r2` always list ascending. This repo has three branches sharing `ImageService` unchanged:
- `main` / `r2` — inject `env.MY_BUCKET` (native R2) directly.
- `webdav` (current) — inject `WebDAVStorage`, which reimplements that same shape over WebDAV HTTP verbs. No R2 binding; `wrangler.toml` has no bucket.

`src/services/WebDAVStorage.js` — translates the R2 interface to `GET` / `PUT` / `MKCOL` / `PROPFIND` / `DELETE`, parsing namespaced XML with `fast-xml-parser`. Notable constraints:
- The constructor's default `request` **must** stay wrapped as `(...args) => fetch(...args)`. Storing bare `fetch` as an instance property makes `this.request(...)` call it with the storage instance as receiver, and workerd throws `TypeError: Illegal invocation` — which `send()`'s catch then disguises as "WebDAV 请求失败或超时". Stub-injected tests cannot catch this; the dedicated receiver test does.
- All keys are confined to `i/`; `validate()` rejects traversal, control chars, backslashes, empty segments. `delete()` refuses to delete a collection.
- `redirect: 'manual'` everywhere — a redirect is an error, never followed, so credentials never leak to another host. XML with `<!DOCTYPE>` / `<!ENTITY>` is rejected (XXE guard).
- `put()` creates each missing parent dir via `MKCOL` (tolerating 405), then re-verifies via `PROPFIND` that a 405 was a real directory and not a same-named file.
- WebDAV has no snapshot pagination. `list()` does a Depth:1 walk, encoding a base64 JSON cursor `{ prefix, dirs, after, order }` (queue of pending dirs + last-seen file + direction). Each call scans ≤35 directories and **may legitimately return an empty `objects` array with a non-null `cursor`** — callers must keep following the cursor.
- `order: 'desc'` reverses both the directory stack and the in-directory filename sort, so the walk runs newest→oldest end to end (keys are time-ordered, see the path scheme below). The cursor records its direction and a mismatched one is rejected as `无效的分页游标` — changing sort order means restarting from a null cursor. `after: ''` means "no bound yet" in both directions.

`src/services/ImageService.js` (~1900 lines) — all business logic: the three upload paths (multipart, JSON/base64, raw binary), date-based path generation (`/i/YYYY/MM/DD/<8-char-base60-time-id><ext>` — 时分秒各 1 位 + 毫秒 2 位 + crypto 随机 3 位；目录日期与文件名时间同用 `TIMEZONE_OFFSET`，故 `ImageService` 的构造函数接收 `env` 作为第二个参数), MIME↔extension mapping for images, video and audio (`_extensionFrom` prefers the original filename's suffix, sanitised to `[a-z0-9]{1,8}`, and falls back to the MIME map), media fetch (passes through remote `Content-Type` / `ETag` / `Last-Modified`, caches 1 day, and forwards the client's `Range` header to WebDAV — the backend's `206` / `Content-Range` / `Accept-Ranges` are passed through so `<video>` can seek), delete, `listImages` (validates `year`/`month`/`day` before building the prefix, defaults to `order: 'desc'`), `listDirs` (the year/month/day filter options, via `_listSubdirs` over `list()`'s `delimiter` branch), and `renderDashboard()` which returns the entire admin UI as an inline HTML string — static, no WebDAV call, with the dashboard's own JS filling the filter selects from `/admin/dirs`. The “auto-follow empty-but-cursor pages, up to 20 rounds” loop lives in that inline JS (`loadImages()`), **not** in `listImages`, which makes exactly one `storage.list()` call.

`src/index.js` also caps the two buffering upload paths (multipart, JSON base64) at `MAX_BUFFERED_UPLOAD` = 20 MB, checked against `Content-Length` **before** the body is parsed — a missing `Content-Length` is a 411, over the cap a 413. The cap is derived from memory, not policy: multipart peaks at ~2–3× the file, base64 at ~4–5×, and the 128 MB isolate is shared across concurrent requests, so raising it turns a clean 413 into an OOM. The dashboard's own uploader uses the raw-binary path (XHR with the `File` as the body, plus an `X-Upload-Filename` header to keep the original suffix) precisely so large media is not subject to that cap. The streaming paths (raw-binary `POST /upload`, `PUT /i/...`) are deliberately uncapped — `request.body` is passed straight through to WebDAV, so only Cloudflare's per-plan request-body limit applies. Large media (video/audio, iPhone ProRAW) must use those.

`src/middleware/AuthMiddleware.js` — static `Bearer` token check. Upload endpoints also accept the token as a `token` form/JSON field (for uPic and similar clients), but the header wins and is checked **before** the body is parsed: an `Authorization` header that is present and wrong is rejected outright, so a doomed request never gets its file buffered into the 128 MB isolate. The body-token fallback applies only when no `Authorization` header is sent at all — that path unavoidably parses first, so an anonymous request can still force a full buffer (a `Content-Length` guard would be the fix). `hasHeader()` is what distinguishes the two cases.

`src/services/McpService.js` — the MCP (Model Context Protocol) server behind `POST /mcp`. Hand-rolled stateless JSON-RPC over Streamable HTTP: no `@modelcontextprotocol/sdk`, no Durable Objects, no new dependency, always a single `application/json` response, never SSE, and **never a `Mcp-Session-Id`** (emitting one makes clients `DELETE /mcp` on shutdown and eat a 405). Constructor is `(imageService, options)` with `options.request` injectable for tests — **that default must stay wrapped as `(...args) => fetch(...args)` for exactly the same `Illegal invocation` reason as `WebDAVStorage`**. `maxBytes` is injected from `src/index.js`'s `MAX_BUFFERED_UPLOAD` rather than imported, to avoid an `index → McpService → index` cycle. Notable points:
- **Protocol era.** MCP moved to a "modern era" at revision `2026-07-28` (no `initialize`, no sessions, per-request `_meta` envelope, `server/discover`). This server deliberately stays legacy-era and advertises `2025-11-25`; unknown methods return **404 + `-32601`**, which is what makes a dual-era client fall back from its `server/discover` probe to `initialize`. Don't "fix" this because a newer spec revision exists.
- **Two error channels.** Protocol errors (unknown method, missing `name`, unknown tool, bad JSON) are JSON-RPC `error` objects. Everything a tool run can hit — blocked URL, unsupported type, oversize, redirect, WebDAV failure — is a **successful** JSON-RPC response carrying `result.isError: true` with a Chinese message, because the spec positions those as feedback the model reads and self-corrects from. Getting this backwards makes the model give up instead of retrying.
- **`source_url` is the SSRF surface.** Checks live in `_validateSourceUrl` / `_fetchRemoteImage`: HTTPS only, no credentials in the URL, no IP literals (a deliberately broad `/^[0-9a-fx.:]+$/i` catches decimal/hex/octal variants), no `localhost` / `.local` / `.internal` / dotless hosts, no self-origin, `redirect: 'manual'` with 3xx treated as an error, status must be exactly 200 (not `res.ok` — 206 would store a truncated file), 15 s timeout, no client headers forwarded, and a size cap enforced **twice** (declared `Content-Length`, then a running byte counter over the stream, since the header may be absent or lying). What is *not* defended, and should not be claimed as such: DNS rebinding (a Worker cannot resolve before fetching), `wrangler dev` reaching the local machine's network for real, and anyone holding `AUTH_TOKEN` being able to use the Worker as an authenticated fetch proxy.
- **SVG is rejected** on the MCP path only. `_getExtension` maps `image/svg+xml`, and an SVG served back from `/i/...` on the Worker's own origin is stored XSS against the dashboard. The three existing `/upload` paths still have this hole — fixing them is a separate change.
- The tool is image-only by design even though the host now accepts video and audio, and `inputSchema` deliberately carries no top-level `oneOf`: the either/or rule is hand-validated in `_uploadImage` so the model gets an actionable Chinese error instead of an opaque schema failure.

`src/services/OAuthService.js` — a stateless OAuth 2.1 authorization server, added for exactly one reason: **claude.ai web and mobile custom connectors cannot send a static `Authorization` header** (that is `static_headers`, still a beta allowlist), they only speak OAuth. ChatGPT's developer-mode connectors are stricter still — OAuth 2.1 or nothing, no API-key or header option at all. Claude Code and Desktop keep using `Bearer <AUTH_TOKEN>`; `/mcp` accepts either credential (`AuthMiddleware.verify` first, then `OAuthService.verifyAccessToken`).

Statelessness is the design constraint, not laziness: this repo has no KV, D1 or Durable Object binding and is not gaining one for this. So there is nothing server-side to look up — every artefact carries its own content, signed with HMAC-SHA256 over a key derived from `AUTH_TOKEN` (`SHA-256("cf-photos-oauth-v1:" + token)`), formatted `base64url(JSON).base64url(sig)`. Consequences that are accepted, not overlooked: individual tokens cannot be revoked (rotate `AUTH_TOKEN` to kill everything); refresh tokens rotate but the old one stays valid until it expires, because nothing records "already used"; authorization codes cannot be single-use for the same reason, and lean on a 10-minute TTL plus PKCE binding instead. The payload's `t` field is part of the signed body, so a code can never be replayed as an access token — `test/oauth.test.mjs` pins that.

- **The consent page is the whole login.** `GET /oauth/authorize` renders a form whose only field is `AUTH_TOKEN`. The image host has exactly one owner; a user table would be theatre, and anyone holding the token could already call `/mcp` directly. Comparison is constant-time over HMAC digests, so neither the value nor its length leaks.
- **Redirect URIs are allowlisted at registration** (`isAllowedRedirect`): the hosts in `ALLOWED_REDIRECT_HOSTS` (`claude.ai`, `claude.com`, `chatgpt.com`) over HTTPS with any path, plus loopback (`localhost`, `127.0.0.1`, `[::1]`, any port, any path — RFC 8252, Claude Code's ephemeral port). Paths are deliberately unconstrained because every vendor moves them (ChatGPT alone has both `/connector_platform_oauth_redirect` and a per-connection `/connector/oauth/{callback_id}`), and pinning a path just turns a vendor change into a 400 at registration; the trust is in the host, which would need its own open redirect to be abused. This is the load-bearing anti-phishing control. Open registration with arbitrary `redirect_uri` would let an attacker register a client pointing at themselves, lure the owner to the consent page, and walk off with the code — **PKCE does not help there**, because the attacker initiated the flow and holds the verifier. The check runs again at `/authorize` so tightening the rules also invalidates old `client_id`s.
- **`client_id` is deterministic** — it *is* the signed registration metadata, so re-registering identical metadata returns the same id and DCR cannot pile up clients. There is nothing to garbage-collect.
- **What the metadata deliberately does and does not advertise.** `code_challenge_methods_supported: ["S256"]` (Claude always sends PKCE) and `token_endpoint_auth_methods_supported: ["none"]` (public client). It does **not** advertise `client_id_metadata_document_supported`, so Claude falls back from CIMD to DCR — intentional, it keeps one outbound fetch out of the flow. `scopes_supported` includes `offline_access` because Claude only asks for a refresh token when it sees it there.
- **The 401 is the discovery entry point.** `OAuthService.unauthorizedResponse()` replaces the generic one on `/mcp` and carries `WWW-Authenticate: Bearer realm=…, resource_metadata="<origin>/.well-known/oauth-protected-resource/mcp", scope=…`. Claude honours `WWW-Authenticate` **only on a 401**, never on a 200. Without the pointer it falls back to probing `/.well-known/*` on the origin, which costs round-trips and only works because those routes happen to exist. The metadata's `resource` must equal the URL the user typed into Claude, character for character, path included.
- **RFC 9207 `iss` is not optional decoration.** `authorization_response_iss_parameter_supported: true` is what makes ChatGPT use its stable redirect URI instead of a per-connection `callback_id` one, and declaring it obliges every authorization response — success *and* error redirects — to carry `iss` equal to the metadata `issuer` character for character.
- Access tokens are audience-bound (`aud` = `<origin>/mcp`) and verified against the live request origin, so a prod token is inert against a dev host and vice versa. An RFC 8707 `resource` parameter (ChatGPT always sends one, Claude may) is rejected with `invalid_target` unless it names this server's own MCP URL — the audience was never negotiable, the check just says so out loud. TTLs: code 10 min, access 30 days, refresh 90 days.
- `/oauth/token` reads `application/x-www-form-urlencoded` (what RFC 6749 and Claude both use) and tolerates JSON. Every failure is an RFC 6749 error object; a dead refresh token must be `invalid_grant` specifically — that is the code Claude keys on to restart the authorization flow.
- All endpoints are pure computation, no outbound requests. That matters: Claude allows 10 s for discovery, registration and token exchange, 30 s for refresh.

`test/mcp.test.mjs` is the repo's first **router-level** integration test: it calls `worker.fetch(new Request(...), env, ctx)` directly and stubs `globalThis.fetch` (restored in a `finally`, same pattern as the receiver test in `webdav.test.mjs`), dispatching by hostname so one stub serves both the WebDAV verbs and the tool's outbound image fetch. Two traps it encodes: `WebDAVStorage.send()` passes a `URL` object while `McpService` passes a string, so the stub must accept both; and `new Request(url, {body})` does not populate `Content-Length` on the request's own headers, which the `/mcp` branch reads.

`fetchImage` 的响应经过安全加固，堵的是存储型 XSS：后台页面与 `/i/...` 同源，`AUTH_TOKEN` 就存在同源的 `localStorage.cf_photo_token` 里，一旦上传内容能在本站域名下执行脚本就等于交出 Token。三步，顺序不能换：① 后端 Content-Type 缺失或为 `application/octet-stream` 时，用 `_mimeFromExtension` 按后缀回填——**这是 `nosniff` 的前提**，不回填就会把后端只回 octet-stream 的正常图片变成白屏；② 类型为空、命中 `RISKY_MIME_TYPES`、或后缀命中 `RISKY_EXTENSIONS` 时，改写为 `application/octet-stream` + `Content-Disposition: attachment`（见下面实测：后端对 `.html` 压根不回 Content-Type，只判 MIME 会漏，所以后缀那一路必须留着）；③ 恒定下发 `Content-Security-Policy: default-src 'none'; script-src 'none'; sandbox` 与 `X-Content-Type-Options: nosniff`。`fetchImage` 只有一处 `new Response`，200 与 206 共用这套头。不加 `Cross-Origin-Resource-Policy`——那会打断外站热链，而热链正是图床要的。

**后端会自己重新推导 Content-Type，别以为浏览器看到的就是我们 PUT 的那个。** 对 teracloud（Apache + `mime.types`）实测：PUT 一个 `.png` 却声明 `application/octet-stream`，GET 回来是 `image/png`；PUT 一个无后缀文件并声明 `image/png`，GET 回来**没有** Content-Type 头。也就是说它忽略我们存的类型，改按**文件后缀**推导。结论：真正的控制点是后缀而不是我们写进 `httpMetadata` 的 MIME——这正是上传侧 `RISKY_EXTENSIONS` 那一半必须存在的原因，只拦 MIME 挡不住。完整实测（左为 PUT 声明，右为 GET 返回）：`.mp4`→`video/mp4`、`.png`→`image/png`、`.svg`→`image/svg+xml`、`.xml`→`application/xml`、`.js` 声明 `text/javascript` 却返回 `application/javascript`（两者都在 `RISKY_MIME_TYPES` 里，已覆盖）、`.html`→**无此头**、`.heic`→**无此头**、无后缀→**无此头**。

两个由此而来的副作用，都是有意接受的：① `.heic` 过去因为后端不回类型只能靠浏览器嗅探显示，现在回填会给它 `image/heic`，是实打实的改善；② 无后缀文件回填不出类型，会落进降级分支变成 `attachment` 下载。写这段时全库 503 个文件的后缀分布是 `.png` 360 / `.jpeg` 74 / `.jpg` 30 / `.webp` 31 / `.gif` 4 / `.mp4` 2 / `.mov` 1 / `.svg` 1，**无后缀文件 0 个**，所以②当前不影响任何东西；但 `uploadWithBase64` 的裸 base64 分支在认不出类型时确实会产出无后缀文件，将来可能碰到。

**SVG 是有意保留的，靠 CSP 而不是靠禁用来防护——别当成遗漏又去把它禁掉。** SVG 在 `<img>` 里本就不执行脚本，只有被当作文档打开时才会，而 `sandbox` 恰好只在那种场景生效。已在真实浏览器里验证：含 `<script>` 的 SVG 直接打开时图形正常渲染，控制台报 `Blocked script execution ... the document's frame is sandboxed`，`window.origin` 为 `"null"`，`localStorage` 访问抛 `SecurityError`；同一文件放进 `<img>` 仍正常加载。因此 `image/svg+xml` 与 `.svg` 刻意**不在** `RISKY_MIME_TYPES` / `RISKY_EXTENSIONS` 里。

上传侧是纵深防御：`_rejectRiskyUpload(contentType, extension)` 在四条路径（`uploadFormData` / `uploadWithBase64` / `uploadWithAutoPath` / `uploadImage`）写盘之前各调用一次，命中返回 415。`PUT /i/...` 的后缀来自客户端指定的 URL，是最直接的一条注入路，单独从 key 里取后缀检查。`McpService` 不接这个守卫——它要求 `mime.startsWith('image/')` 且显式拒绝 SVG，本来就更严。注意后台页面的 `MEDIA_PREFIXES` 只是前端提示，curl 可绕，服务端这层才是真的。

`MIME_MAP` 在模块作用域，`EXTENSION_TO_MIME` 由它反转而来（同后缀多 MIME 时先到先得，如 `.jpg` 取 `image/jpeg`）。加后缀或类型只改 `MIME_MAP` 一处，别再起第二张表。

`scripts/scan-risky-files.mjs` 是配套的只读盘点脚本，直连 WebDAV（读 `.dev.vars`，不依赖 dev server），跟着 `list()` 的游标走到底列出存量里的危险后缀。它必须处理「`objects` 为空但 `cursor` 非 null」的分页语义，漏了会漏报深层目录。

## Endpoints

`GET /` dashboard · `POST /upload` (multipart `image`/`file`, or JSON base64, or raw binary) · `GET /i/{y}/{m}/{d}/{name}` fetch · `PUT /i/...` upload to explicit path · `GET /admin/list?limit&cursor&year&month&day&order` (`order=desc` newest-first, the default; `asc` oldest-first) · `GET /admin/dirs?year&month` (filter options: no params → years, `year` → that year's months, `year`+`month` → that month's days; descending) · `DELETE /admin/delete/{key}` · `POST /mcp` (stateless MCP Streamable HTTP, one tool `upload_image`; `OPTIONS` preflight; `GET`/`DELETE` return 405 + `Allow: POST`, never the generic 404) · OAuth: `GET /.well-known/oauth-protected-resource[/mcp]`, `GET /.well-known/oauth-authorization-server[/mcp]`, `POST /oauth/register`, `GET`+`POST /oauth/authorize`, `POST /oauth/token` (all anonymous by necessity, all 503 without `AUTH_TOKEN`).

## Verifying WebDAV changes

Beyond `npm test`: with real `.dev.vars`, upload a throwaway image, confirm the downloaded bytes match, check it appears first in `/admin/list` (default newest-first), last under `order=asc`, and in a `year`+`month`+`day` filtered query whose values `/admin/dirs` reports, then delete it and confirm a subsequent fetch returns 404.

For MCP changes, additionally: `initialize` echoes a supported version and falls back to `2025-11-25` for an unknown one; `notifications/initialized` returns a bodyless 202; `tools/list` shows exactly `upload_image`; `tools/call` with `image_base64` and with `source_url` both return `isError: false` and a URL that actually fetches back byte-identical; every blocked `source_url` (plain http, `https://127.0.0.1/…`, `https://2130706433/…`, `https://localhost/…`, the Worker's own host, a redirect, a non-image type) returns **HTTP 200 with `result.isError: true`**, not a JSON-RPC error; `GET`/`DELETE /mcp` return 405; a tokenless POST returns 401 with `WWW-Authenticate`; and with `AUTH_TOKEN` commented out of `.dev.vars`, `POST /mcp` returns 503 while `GET /` still works. Finally connect for real — `claude mcp add --transport http cf-photos-dev http://127.0.0.1:8787/mcp --header "Authorization: Bearer $TOKEN"`, then `/mcp` in a session — and watch the `wrangler dev` console for the `server/discover` 404 followed immediately by `initialize`. If a client ever fails to connect there, the knob to flip is the HTTP status for unknown methods (404 → 200, keeping 404 only for `server/discover`).

For OAuth changes, run `test/oauth.test.mjs` and then walk the real flow against `wrangler dev` (nothing here touches WebDAV, so it is safe to poke at): the two `.well-known` documents come back with `resource` = `<origin>/mcp` and `code_challenge_methods_supported: ["S256"]`; an unauthenticated `POST /mcp` returns 401 whose `WWW-Authenticate` carries `resource_metadata=`; `POST /oauth/register` returns 201 for a `claude.ai` callback and 400 `invalid_redirect_uri` for anything else; the consent page renders, rejects a wrong token with a 401 and **no** `Location`, and on the right token 302s to the callback with `code` and the original `state`; the code exchanges for a token pair with the matching `code_verifier` and fails `invalid_grant` without it; the access token then drives `tools/list`; the refresh token yields a working new pair; and `Bearer <AUTH_TOKEN>` still works throughout.
